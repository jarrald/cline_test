# Stress and Load Test Plan

Goal: make performance claims falsifiable. Two tools are supported:

1. **k6** (`deploy/load/k6.js`) - industry standard, used when available.
2. **built-in generator** (`services/load_generator`) - zero dependencies, used
   by CI and by the reliability tests, so the plan is executable anywhere.

Both drive the same public contract: `POST /api/v1/orders` through the edge LB.

## Service level objectives (SLOs)

| SLO | Target | Measured by |
|---|---|---|
| Availability under nominal load | >= 99% 2xx/202 | load generator `success_rate` |
| Latency p95 (nominal) | < 500 ms | load generator percentiles |
| Latency p99 (nominal) | < 1000 ms | load generator percentiles |
| Error budget during single pod loss | <= 1% failures | reliability test |
| Recovery time after pod kill (RTO) | < 10 s | kpilot `pod_started` -> `pod_ready` events |
| Data loss | 0 accepted orders | order status projection + broker lag |
| Consumer lag after quiesce | 0 within 30 s | broker `/topics/{t}/stats` |

## Capacity model (why the numbers are what they are)

Little's law: `inflight = throughput x latency`. With 120 ms simulated I/O and
`MAX_CONCURRENCY=8` per pod, one order-service pod saturates at `8 / 0.12 ~ 66
rps`. HPA target inflight is 2.8/pod, so 100 rps with 2 pods yields
`100 x 0.12 / 2 = 6 inflight/pod` -> desired replicas `ceil(12 / 2.8) = 5`.
That is a deliberate, reproducible overload.

## Scenarios

### S1 - Baseline / smoke
* 20 rps, 8 workers, 30 s, warm cluster.
* Pass: p95 < 500 ms, success >= 99.5%, inflight stable, zero 5xx.
* Purpose: prove the happy path and give a latency floor.

### S2 - Ramp
* 10 -> 120 rps over 60 s (step 10 rps every 5 s).
* Pass: success >= 99%, HPA scales up as inflight crosses target, no rejected
  requests at the gateway except when deliberately beyond capacity.
* Purpose: show graceful degradation and scale-out before saturation.

### S3 - Spike
* Baseline 20 rps for 10 s, then 150 rps for 20 s, then back to 20 rps.
* Pass: `hpa_scale_up` within 10 s; p95 during spike < 1500 ms; error rate < 2%;
  scale-down begins after cooldown and does not oscillate.
* Purpose: the autoscaling demo, also the reliability test's scenario.

### S4 - Soak
* 40 rps for 15 min (nightly CI).
* Pass: no upward drift in `inflight`, latency p95 stable, RSS growth < 20%,
  no fd leak (`/proc/<pid>/fd` count stable), replication never falls behind by
  more than one revision, zero dead letters.
* Purpose: catch leaks and unbounded queues.

### S5 - Dependency failure: storage primary
* Kill `storage-shard-0-primary` while 40 rps runs.
* Pass: replica promoted (`storage_primary_failovers_total` increments), reads
  never fail, write failures <= 1% and only during promotion, recovery < 10 s.
* Trade-off documented: client-side promotion is not consensus (ADR 0004).

### S6 - Dependency failure: message broker backpressure
* Scale `inventory-worker` to 0, publish until `MAX_BACKLOG` is exceeded.
* Pass: broker returns 503 + `Retry-After`; gateway surfaces 503/429 with the
  header; no process crashes; after workers return, lag drains to 0 and accepted
  orders reach a terminal state.
* Purpose: prove backpressure is end-to-end, not just a broker detail.

### S7 - Consumer crash
* SIGKILL `inventory-worker-1` mid-stream (partition owner).
* Pass: kpilot restarts it, offsets resume (at-least-once), no stock is
  decremented twice (idempotency key), no order is lost.

### S8 - Gateway / edge saturation
* Push 400 rps with gateway `MAX_CONCURRENCY=64` (2 replicas) and
  `RATE_LIMIT_RPS=400`.
* Pass: overload produces fast 429/503 responses (no unbounded latency), p99 for
  rejected requests < 50 ms, retries do not amplify load (breaker opens).

## Metrics captured for every run

* load generator: achieved rps, status histogram, p50/p95/p99/max, upstream pod spread
* kpilot: replica timeline from `events.jsonl` (`hpa_scale_up`, `pod_ready`, ...)
* broker: per-partition high watermark, group lag, dead-letter count
* storage: per-shard key counts, replication failures, failover events
* services: `mesh_inflight`, `mesh_cpu_percent`, `http_request_duration_seconds`

Artifacts: `docs/results/<scenario>-<timestamp>.json` (raw) and `.md` (summary
table) generated by `scripts/stress.py`; committed so results are reviewable.

## Interpreting results honestly

* A scale-out event is not a pass by itself; latency and error rate must recover.
* Shared CI runners are noisy: assert behaviour (scaled / healed / no loss) with
  generous latency budgets; run tight latency SLOs on a dedicated host.
* SQLite is single-writer per shard; throughput ceilings in this demo are set by
  simulated I/O, not by the database engine. The plan names that limitation
  instead of hiding it.
